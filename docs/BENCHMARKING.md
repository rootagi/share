# Benchmarking `share`

This guide explains how to measure `share`'s throughput, concurrency scaling, and memory usage on both loopback (isolating application, disk/cache, and TLS overhead) and a real LAN (Wi-Fi or Ethernet), how to identify the bottleneck in each layer, and records actual loopback measurements taken on the build host.

> **Important Note on Claims**: `share` does **not** use kernel `sendfile(2)` / zero-copy I/O (which is incompatible with user-space `rustls` TLS and not exposed by `hyper`'s stream body abstraction), and does **not** guarantee a fixed MB/s figure because real-world throughput depends on your network link, storage medium, CPU, and TLS cipher performance. Instead, `share` streams data in 256 KiB chunks (`ReaderStream`) on downloads and 1 MiB buffered writes (`BufWriter`) on uploads so memory usage remains small and independent of file size.

---

## 1. Establish Baselines First (`iperf3` & `dd`)

Before benchmarking `share`, measure the raw network ceiling and raw storage ceiling separately so you know what 100% looks like on your hardware.

### Network ceiling with `iperf3`

On the server machine:

```bash
iperf3 -s
```

On the client machine:

```bash
# Single TCP stream
iperf3 -c <SERVER_IP> -t 10

# 4 parallel TCP streams (tests multi-queue NIC / Wi-Fi aggregation)
iperf3 -c <SERVER_IP> -P 4 -t 10
```

Typical ceilings:
- **1 GbE Ethernet**: ~940 Mbps (~117 MB/s) after TCP/IP framing overhead.
- **2.5 GbE Ethernet**: ~2.35 Gbps (~293 MB/s).
- **Wi-Fi 5 (802.11ac, 2x2, 80 MHz)**: ~300–600 Mbps (~37–75 MB/s) at close range; lower through walls or on congested channels.
- **Wi-Fi 6 (802.11ax, 2x2, 80/160 MHz)**: ~600–1,200 Mbps (~75–150 MB/s).

### Disk & page-cache ceiling with `dd`

On the server machine, create a test file and measure sequential read speed:

```bash
# Write a 2 GiB test file
dd if=/dev/zero of=/tmp/bench.bin bs=1M count=2048 conv=fdatasync status=progress

# Warm read (from Linux page cache / tmpfs)
dd if=/tmp/bench.bin of=/dev/null bs=256k status=progress

# Cold read (drop page cache first — requires root)
sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'
dd if=/path/on/disk/bench.bin of=/dev/null bs=256k status=progress
```

## 2. Single-Client Benchmarks (`curl`, `wget`, `pv`)

Start `share` in headless mode so terminal rendering does not share CPU on single-core/dual-core machines:

```bash
# HTTPS (default)
./target/release/share /tmp --no-tui --port 8080

# Or plain HTTP (to isolate TCP/HTTP from TLS encryption)
./target/release/share /tmp --http --no-tui --port 8080
```

### Measure download throughput with `curl`

Discard the payload to `/dev/null` so client disk write speed cannot bottleneck the test:

```bash
curl -ksS -o /dev/null \
  -w 'size=%{size_download} B  time=%{time_total}s  speed=%{speed_download} B/s\n' \
  https://<SERVER_IP>:8080/download/bench.bin
```

### Measure download throughput with `wget`

```bash
wget --no-check-certificate -O /dev/null https://<SERVER_IP>:8080/download/bench.bin
```

### Live throughput & progress inspection with `pv`

Pipe `curl` into `pv` to watch instantaneous throughput variance and total bytes transferred:

```bash
curl -ksS https://<SERVER_IP>:8080/download/bench.bin | pv > /dev/null
```

### Measure upload throughput with `curl` and `dd`

Start `share` with `--upload`:

```bash
./target/release/share /tmp --upload --no-tui --port 8080
```

Upload a file from disk:

```bash
curl -ksS -H 'X-Share-Upload: 1' \
  --data-binary @/tmp/bench.bin \
  -w 'time=%{time_total}s  speed=%{speed_upload} B/s\n' \
  'https://<SERVER_IP>:8080/api/upload?name=upload-bench.bin'
```

Or stream generated bytes directly from `dd` through `pv` into `curl` without touching client disk:

```bash
dd if=/dev/zero bs=1M count=1024 status=none \
  | pv \
  | curl -ksS -H 'X-Share-Upload: 1' -T - \
      'https://<SERVER_IP>:8080/api/upload?name=streamed.bin'
```

## 3. Multi-Client Concurrency Benchmark (`scripts/bench.sh`)

The repository includes [`scripts/bench.sh`](../scripts/bench.sh), which spawns `1`, `2`, `5`, and `10` concurrent `curl` processes (or any custom client counts passed on the command line) and reports both the **aggregate server throughput** (total bytes across all clients divided by wall-clock elapsed time) and the **mean per-client throughput**:

```bash
# Default concurrency sweep: 1, 2, 5, and 10 concurrent clients
scripts/bench.sh https://<SERVER_IP>:8080 bench.bin

# Explicit concurrency levels
scripts/bench.sh http://127.0.0.1:8080 bench.bin 1 2 5 10
```

Run `scripts/bench.sh`:
1. **On loopback (`127.0.0.1`)** to measure the server + TLS + kernel socket ceiling without physical NIC limits.
2. **From another machine on the LAN** to measure actual end-to-end Wi-Fi or Ethernet performance.

## 4. Measuring Memory (RSS) During Multi-GB Transfers

To verify that `share` streams without buffering whole files in memory, create a multi-gigabyte sparse file (which occupies 0 bytes on disk but reads back as `N` GiB of zeros) and monitor the server's Resident Set Size (`VmRSS`) and kernel High-Water Mark (`VmHWM`) in `/proc/<pid>/status`:

```bash
truncate -s 8G /tmp/sparse8g.bin
./target/release/share /tmp --http --no-tui --bind 127.0.0.1 --port 8080 &
SRV_PID=$!

# Before transfer
grep -E 'VmRSS|VmHWM' /proc/$SRV_PID/status

# Stream all 8 GiB while sampling VmRSS every 50 ms
curl -sS -o /dev/null http://127.0.0.1:8080/download/sparse8g.bin &
CURL_PID=$!
while kill -0 $CURL_PID 2>/dev/null; do
  grep VmRSS /proc/$SRV_PID/status
  sleep 0.05
done

# After transfer
grep -E 'VmRSS|VmHWM' /proc/$SRV_PID/status
kill -TERM $SRV_PID
```

Because `FileStream` holds only a single 256 KiB `ReaderStream` buffer per connection, `VmRSS` stays flat at a few megabytes across an 8 GiB (or 100 GiB) transfer.

## 5. How to Identify the Bottleneck

When transfer speed is lower than expected, compare five measurements to isolate the limiting factor:

| Suspected Bottleneck | How to Test / Diagnose | Symptoms & Fix |
| :--- | :--- | :--- |
| **Wi-Fi link** | Compare `iperf3 -c <SERVER_IP>` over Wi-Fi vs. loopback. Check `iw dev wlan0 link` for MCS index, channel width (20/40/80/160 MHz), signal (`dBm`), and retries. | `share` download speed is within ~85–95% of `iperf3` speed. Wi-Fi is half-duplex and shared; move closer to the AP, use 5 GHz / 6 GHz instead of 2.4 GHz, or wire at least one endpoint to Ethernet. |
| **Ethernet link** | Check negotiated link speed with `ethtool eth0` (`Speed: 1000Mb/s` vs `100Mb/s` or `2500Mb/s`) and run `iperf3`. | Throughput plateaus cleanly at ~11.5 MB/s (100 Mbps cable/switch port), ~115 MB/s (1 GbE), or ~290 MB/s (2.5 GbE). |
| **Disk / Storage** | Compare downloading a file in `/dev/shm` (RAM tmpfs) vs. the real filesystem, or watch `iostat -xz 1` (`%util`, `r_await`, `w_await`) during transfers. | Fast from `/dev/shm` but slow from disk, or `iostat` shows ~100% device utilization (common with spinning HDDs, USB 2.0 drives, or concurrent random reads). |
| **TLS encryption** | Compare `share --http` vs. default `share` (HTTPS) on loopback (`127.0.0.1`). | Plain `--http` is significantly faster than HTTPS while a CPU core hits 100% user time. On low-power CPUs without AES-NI (or when saturating 10 GbE), pass `--http` on trusted LANs. |
| **Server CPU** | Run `top -H -p $(pidof share)` during a transfer to inspect `share-worker` threads. | One or more `share-worker` threads pinned near 100% CPU (or high `sy` kernel time on loopback when both `share` and `curl` share the same cores). |
| **Client (`curl` / browser / disk)** | Write to `-o /dev/null` instead of disk; test with 2–5 concurrent clients (`scripts/bench.sh`) or from a faster client device. | Writing to a slow phone SD card or single-stream browser download caps throughput while aggregate throughput with 2–5 clients is higher.Also note `--http2` vs default HTTP/1.1: HTTP/1.1 avoids HTTP/2 flow-control window framing for single large streams. |

## 6. Measured Loopback Results

The following measurements were recorded on the build machine using `./target/release/share` (`rustc 1.91`, `opt-level = 3`, `lto = "thin"`):

### Test Environment

- **OS / Kernel**: Linux 7.0.0-38-generic x86_64
- **CPU**: Intel Celeron N4020 @ 1.10 GHz (2 cores, shared between the `share` server and the `curl` client processes on loopback)
- **RAM**: 6.8 GiB

### Single 8 GiB Sparse-File Transfer & RSS Memory

File: `8 GiB` (`8,589,934,592` bytes) created with `truncate -s 8G`, downloaded via `curl -o /dev/null` over `127.0.0.1`:

| Mode | File Size | Elapsed Time | Measured Throughput | Idle `VmRSS` | Peak `VmHWM` During 8 GiB Transfer |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **HTTP (`--http`)** | 8 GiB (`8,589,934,592 B`) | `8.27 s` | **1,039.1 MB/s** (`1.04 GB/s`) | `6,592 kB` (~6.4 MiB) | **`6,592 kB` (~6.4 MiB)** |
| **HTTPS (TLS)** | 8 GiB (`8,589,934,592 B`) | `29.91 s` | **287.1 MB/s** | `7,528 kB` (~7.4 MiB) | **`7,528 kB` (~7.4 MiB)** |

Additionally, during a separate 4 GiB HTTP transfer sampled every 50 ms (77 live `/proc/<pid>/status` samples while streaming), `VmRSS` started at `6,504 kB` (~6.4 MiB) and peaked at `9,096 kB` (~8.9 MiB). Across all single-stream and 10-client concurrency runs combined, server `VmHWM` never exceeded `15,800 kB` (~15.4 MiB) in HTTP mode and `16,556 kB` (~16.2 MiB) in HTTPS mode.

### Concurrent Clients (`scripts/bench.sh`, 512 MiB File on Loopback)

Command: `scripts/bench.sh <URL> bench512m.bin 1 2 5 10` (512 MiB file per client; server and `N` `curl` clients sharing the same 2-core CPU):

#### Plain HTTP (`--http`)

| Concurrent Clients | Aggregate Throughput | Mean Per-Client Throughput |
| :--- | :--- | :--- |
| **1 client** | **440.0 MB/s** | **455.8 MB/s** |
| **2 clients** | **445.3 MB/s** | **226.9 MB/s** |
| **5 clients** | **713.4 MB/s** | **146.9 MB/s** |
| **10 clients** | **619.3 MB/s** | **63.9 MB/s** |

#### HTTPS (Default Self-Signed TLS)

| Concurrent Clients | Aggregate Throughput | Mean Per-Client Throughput |
| :--- | :--- | :--- |
| **1 client** | **270.5 MB/s** | **274.9 MB/s** |
| **2 clients** | **283.8 MB/s** | **145.7 MB/s** |
| **5 clients** | **278.9 MB/s** | **57.0 MB/s** |
| **10 clients** | **250.5 MB/s** | **25.4 MB/s** |

*(Note: On loopback on a 2-core Celeron N4020, every byte in HTTPS mode is encrypted by `share` and decrypted by `curl` on the same two CPU cores, making TLS CPU-bound around ~270–287 MB/s—still more than 2x the ~117 MB/s line rate of Gigabit Ethernet.)*

## 7. What `cargo test`, `cargo clippy`, and `cargo fmt --check` Check

- **`cargo test`**: Builds and runs 74 unit tests (`src/`) and 41 integration tests (`tests/integration.rs`, `tests/downloads.rs`, `tests/uploads.rs`), verifying CLI flag conflicts, path traversal and symlink escape blocking, hidden/temp file filtering, natural sorting, pagination, recursive search, RFC 9110 `Range` / `If-Range` / `If-None-Match` / `HEAD` semantics, 64-bit offsets on $>4\text{ GiB}$ sparse files, byte-exact resumed downloads, concurrent downloads and uploads, client disconnect cleanup, live speed sampling, CSRF header enforcement, TLS certificate generation/validation, and TUI layout rendering.
- **`cargo clippy --all-targets -- -D warnings`**: Runs the Clippy static analyzer across the library, binary, and all test targets, rejecting any lint warning as a compile error.
- **`cargo fmt --check`**: Checks that all Rust source and test files match standard `rustfmt` style without modifying any files.
